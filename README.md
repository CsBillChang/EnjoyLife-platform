面向本地商户与消费者，提供店铺查询、优惠券秒杀、下单支付和到店核销。消费者能够查找店铺并购券消费；商家能够发布促销活动、核验消费券、查询订单与退款记录。后端重点处理热门店铺查询压力、限量抢购的库存约束及支付履约中的状态冲突。

**状态：L00–L14 工程范围、简历对齐补充与 pprof 分析已在本机验收（2026-09-22）。** 当前已有活动列表/详情的 Ristretto→Redis→MySQL 两级展示缓存（详情负缓存、singleflight、单店单调 generation）、同事务持久失效任务及带租约/退避/poison 隔离的本进程 dispatcher；商家只能修改自己活动的标题，交易条件不可改。购买准入由 Redis Lua 在 schema 2 元数据下校验受理窗口、Redis TIME 截止、generation、资格和 sentinel，MySQL 仍决定订单事实。另已提供用户支付记录、商户核销记录的权限过滤 keyset 分页查询。固定 60 秒本地负载下，**店铺详情旧版本路径**三轮中位 P95 从 33.427 ms 降到 5.179 ms，完整响应吞吐中位约为 4.03 倍；本轮未重跑或宣称活动/优惠券缓存性能收益。500 用户异步成单的“受理到订单行创建” P95 为 4.096 s，非事务 commit 时间。pprof 有效样本未发现显著业务锁热点；typed response 将 handler 微基准从 25 降至 20 allocs/op，但正式 HTTP 对照未显示稳定 P95 或吞吐提升。详见[量化报告](docs/benchmark-report.md)和[pprof 报告](docs/profiling-report.md)。这些均为单机 Docker 与模拟支付结果，不代表真实商户、支付渠道、生产 SLA 或上线规模。

## 一条可以演示的业务流程

```text
消费者查询店铺与活动 → 抢购优惠券 → 获得待支付订单
  → 模拟支付成功 → 到店出示券码 → 所属商家核销
  ├─ 未支付超时：关闭订单、释放一次库存
  └─ 已支付未核销：申请退款，成功后释放一次库存
```

每用户每活动最多成功创建一单；订单关闭或退款后也不重购，未成单失败可新建请求重试。只有所属商家能核销本店、已支付且未退款的券。退款和核销竞争时只能一个流程取得资格。

## 技术与业务的对应关系

| 技术 | 本项目具体用途 |
| --- | --- |
| Go、Gin | HTTP 接口、参数绑定、身份中间件；按业务拆分店铺、活动、购买、订单和核销处理 |
| GORM、MySQL | 保存店铺与交易事实；条件更新扣库存、唯一约束防重复下单、事务处理状态竞争 |
| Redis、Ristretto | Redis 共享缓存与 Go 进程内热点缓存，支持空值缓存、过期兜底及有限陈旧的展示查询 |
| singleflight | 合并同一进程内相同键的回源请求，缓解热点同时过期的数据库压力 |
| Redis Lua | 原子处理抢券资格预占、按请求幂等释放，以及用户、活动限流；不替代 MySQL 成单事务 |
| RabbitMQ、Outbox | 将购买受理与创建订单分开，处理消息重复、发布中断和消费恢复 |
| Goroutine、context、pprof | 有界后台处理、依赖超时、退出控制以及真实负载下的瓶颈定位 |
| Docker Compose | 使用独立 `huixiang-life` 项目、网络、数据卷与宿主机端口组织 MySQL、Redis、RabbitMQ |

参考 Java 项目的业务后，HTTP 框架对应为 Gin，数据库访问对应为 GORM，Caffeine 对应为 Go 的 Ristretto；保留 RabbitMQ 组织异步下单。没有将 Java 专属库名直接放入 Go 简历。

## 分阶段理解请求链路

第一阶段 L00–L03：内存店铺 CLI → Gin HTTP → MySQL 读写 → 登录与商家权限。

第二阶段 L04–L08：缓存查询 → 同步事务下单 → 模拟支付和核销 → 超时关闭与退款。先确认一条交易正确，再引入异步化。

最终阶段 L09–L14：

```text
登录与限流 → MySQL 持久化购买请求 → Redis Lua 资格预占
  → MySQL 事务记录准入状态与 Outbox → RabbitMQ
  → 有界 Worker → MySQL 事务扣库存、创建订单、更新请求结果
  → 消费确认；消费者按请求编号查询结果 → 支付、核销或退款
```

Lua 成功只表示获得入口资格；HTTP 202 也不表示订单已创建。MySQL 的库存条件扣减与唯一约束决定成交。系统允许消息重复，通过业务幂等收敛结果；购买请求在预占前持久化，使预占后进程中断仍可定位和恢复。

## 可讲清的改进与验证

围绕冷热点店铺访问比较缓存前后的完整响应延迟和回源次数；围绕限量抢券验证不超卖、不重复成单；围绕异步请求分别记录“受理到订单行创建”与“受理到首次观察终态”，不把 HTTP 202 或事务内时间戳写成精确提交延迟；围绕支付、关闭、退款和核销验证重复请求与并发状态竞争。实测数据、无效轮次和局限统一见[量化报告](docs/benchmark-report.md)，简历可用表述见[resume-evidence.md](docs/resume-evidence.md)。

从旧版升级时，已存在的 Redis 准入代际缺少 schema 2 元数据或库存回补去重 sentinel，新代码会 fail-closed。需对这些活动执行 fenced rebuild，不能直接补键；重建会将旧 generation 中无订单的 `RECEIVED/ADMITTED` 请求安全失败，所有历史成单用户仍保留限购；新建/已重建代际无此限制。

项目不要求先完成前端。使用接口请求、后台日志、数据库查询和本地模拟器即可逐步演示业务。没有实现的命令、依赖和表不能当成已完成成果。
