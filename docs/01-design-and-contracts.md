# 01｜业务与技术契约

项目：惠享生活 · Go 本地生活服务平台。更新日期：2026-09-22。本文是当前业务与恢复契约；实现状态见 [进度记录](03-progress.md)，实测数值见 [量化报告](benchmark-report.md)。

## 1. 业务范围与角色

消费者查找店铺、浏览优惠活动、抢购消费券、付款、展示券码，并可对已支付未核销的券申请退款。商家维护自己店铺的资料和活动，核销本店消费券，查看本店交易记录。平台管理员负责基础商户维护和异常查询；首版无需复杂运营后台。

闭环为“店铺发现 → 购券 → 支付 → 到店核销”，以及未支付关闭和未核销退款。采用普通账号身份、店铺归属与业务权限控制，不另建租户订阅或通用回调产品。先做模块化单体 Go 服务与后台 Worker，支付、退款由本地模拟器验证。

- 每活动一类券、每单一张券、每用户每活动最多成功创建一单。关闭或退款不恢复该用户购买资格；未成单失败可用新请求再次尝试。
- 下单时锁定活动价格快照；金额为整数最小货币单位，不接受客户端指定成交价。活动开抢后不在本轮扩展改价、改总库存和叠加优惠。
- 活动结束禁止新购买，但开抢期间已受理的请求可在既定处理期限内完成。受理、成单、支付和券使用各有独立状态与截止时间，活动结束不自动作废已购券。
- 核销仅限已支付、未核销且未进入退款的有效券；商家身份必须与订单店铺匹配。券码随机且不可由顺序订单号猜出，日志不明文记录完整券码。
- 已核销订单不能在本轮普通退款流程中退款。商家线下结算、真实渠道资金和复杂售后不作为首版已交付功能。

## 2. 事实来源与数据模型

**MySQL 是业务事实来源。** Redis 展示缓存允许有限陈旧；秒杀缓存只管理准入资格。RabbitMQ 传递处理通知，不能保存唯一的购买事实。

| 目标表/实体 | 关键事实与约束 |
| --- | --- |
| users、merchant_shop_members、shops | 登录身份与商家店铺归属；按身份过滤可操作店铺 |
| coupon_activities | 店铺、价格、活动时段、券使用期限、total_stock、available_stock、准入开关与 generation |
| purchase_requests | request_id、用户、活动、幂等键及参数摘要、状态、处理期限、generation、结果订单与错误原因 |
| orders | 价格和店铺快照、支付截止、交易状态；唯一 request_id、唯一 `(user_id, activity_id)` |
| inventory_movements | 成单扣减与释放记录；每订单每 kind 唯一，关单与退款共用一种 `RELEASE` |
| payments、refunds | 渠道/模拟器交易身份、金额、支付事实和退款状态；稳定外部请求号与回调去重约束 |
| vouchers、redemptions | 券与订单一对一；券码存摘要；核销记录唯一 voucher_id，并记录操作商家 |
| outbox、recovery_tasks | 与业务变更同事务记录的待发送消息、缓存失效或资格回补任务及恢复状态 |

幂等键按已认证用户与操作作用域唯一，重复键且参数相同返回同一请求结果；重复键但活动或参数不同返回冲突。所有订单读取使用认证用户或商家归属条件，不相信请求自报 user_id。事务写入先确定锁顺序，库存与状态更新检查影响行数。

库存恒等式：`available_stock = total_stock - 已提交扣减数 + 已提交RELEASE数`。每订单最多一次扣减和一次释放；available_stock 始终在 0 与 total_stock 之间。Redis 预占数不直接写进该恒等式。

## 3. API 与业务可见状态

以下是当前已实现的主要接口与业务结果；运行前由项目本地环境变量设置演示密码，不在文档或仓库中保存真实凭证。

| 接口示意 | 业务结果 |
| --- | --- |
| `GET /shops`、`GET /shops/{id}` | 分页查店与详情，校验分页边界；不存在为 404 |
| `GET /shops/{id}/activities`、`GET /activities/{id}` | 展示活动列表及详情；列表/详情均可走活动展示缓存，缓存库存和价格仅为提示 |
| `POST /purchase-requests` | 认证用户携带 Idempotency-Key 购买；异步受理返回 202 与 request_id，不保证成单 |
| `GET /purchase-requests/{id}` | 仅本人可查处理状态、失败原因或成功订单号 |
| `GET /orders/{id}`、`POST /orders/{id}/payment-attempts` | 查看本人订单，发起有稳定请求号的模拟支付 |
| `POST /orders/{id}/refunds` | 本人对符合条件的订单申请退款，返回可查询的退款状态 |
| `POST /orders/{id}/voucher/reissue` | 支付响应丢失时，仅本人可对 PAID/有效券重新签发；旧码立即失效 |
| `POST /merchant/redemptions` | 商家提交券码，原子核销本店有效券 |
| `GET /me/payment-records` | 本人支付记录的 keyset 分页；游标不扩大数据归属 |
| `GET /merchant/redemption-records?shop_id=` | 所属商家的本店核销记录 keyset 分页；非成员隐藏为 404 |
| `PATCH /merchant/activities/{id}` | 仅所属商家可修改活动标题；价格、时段、库存、券有效期和 generation 等交易条件不可改 |

L06 同步基线只有成单事务提交后返回 201 和订单号；L09 变为查询请求结果。异步请求状态为 `RECEIVED → ADMITTED → SUCCEEDED/FAILED`，RECEIVED 也可直接 FAILED；暂时故障保留处理中状态，不伪装失败又偷偷成单。202 仅说明请求已持久化、正在处理；ADMITTED 才代表通过准入，两者均不是支付或成单成功。

参数错误为 400；缺少或无效身份为 401；无权操作为 403（敏感资源可统一隐藏为 404）；幂等参数冲突/业务状态冲突为 409；入口限流为 429；依赖未就绪为 503。依赖失败后已提交的请求必须可查询，不因客户端超时回滚已存在的订单。

## 4. 店铺与活动展示缓存、失效与回源

查询链路为 `Ristretto → Redis → MySQL`。店铺详情和活动列表/详情均走此展示路径；活动列表 key 含店铺单调 generation，详情 key 含活动 ID。活动详情不存在时可缓存空值，正常展示 TTL 为 30 秒、负缓存 TTL 为 10 秒。用户私有订单、支付和交易权限不混入公共缓存。

- TTL 固定为 30 秒、空值 TTL 固定为 10 秒，当前没有 TTL 抖动；数据创建或变更时也失效相应负缓存。
- 热点展示值含逻辑过期和不可延长的硬过期时间；逻辑过期可短暂返回旧值并有界重建，超过硬过期不能无限续用旧值。向 L1 复制时保留原有效期，不能通过 L1/L2 互相填充无限续命。
- singleflight 只合并同进程同键回源；后台重建也受 Worker 和队列上限约束。跨实例请求不承诺只访问一次数据库。
- Redis 不可用时，店铺查询通过有界回源与限流访问 MySQL；数据库也不可用时按明确的陈旧展示策略或受控错误处理。资格预占 Redis 失效采用暂停购买入口的另一套规则。
- 商家标题更新先在 MySQL 事务写业务数据与 `COUPON_CACHE_INVALIDATE` recovery task；提交后本实例 dispatcher 删除 Redis 与 L1。任务使用 lease token、失败退避、有限次数和 poison 隔离；任务 payload generation 与当前行不一致时不删除新代缓存。没有 Pub/Sub 或跨实例 L1 广播，实例离线或删除失败靠任务重试及有限 TTL 收敛，不宣称强一致。
- Ristretto 允许缓存写入未被接纳，Set 不是业务提交依据；未命中必须能正确回源。删除缓存不撤销已提交业务。

交易时重新查询活动价格、状态、库存和用户权限。展示缓存的陈旧价格不能直接决定扣款金额。

## 5. 先同步成单，再异步化

L06 先用 MySQL 事务锁定活动，检查时段和用户限购，执行带 `available_stock > 0` 条件的扣减，再插入订单及扣减流水。同一事务失败全部回滚；唯一约束冲突不能留下已扣库存。L07–L08 先完成同步流程的支付、关单、核销与退款验证。

L09 增加购买请求与 Outbox：同事务校验活动时段、受理请求、固定价格与服务端 accepted_at、写待处理消息；后台执行库存和订单事务，并把请求结果一并提交。异步成单按 accepted_at 判断开抢窗口，不直接复用 L06 对当前时间的判定；按当前时间判断 processing_deadline。超期未成单只能在锁定请求、确认无已提交订单后终止，避免稍后又被 Worker 成单。

L10 才在异步链上加入 Redis Lua 资格预占：

```text
身份与参数校验、活动/用户限流
 → MySQL 校验受理时段并保存 RECEIVED 请求、accepted_at 和 processing_deadline
 → Lua 以 schema 2 元数据按 `start <= accepted_at < end` 校验开抢窗口，并以 Redis TIME 校验当前时间 `< processing_deadline`，再校验准入开关、generation、库存提示、用户占位和 sentinel
 → MySQL 事务校验当前活动代际，标记 ADMITTED、写 Outbox
 → RabbitMQ 发布与确认 → Worker 查询当前持久请求
 → MySQL 事务条件扣库存、插订单和流水、更新请求 SUCCEEDED
 → 提交后 Ack；客户端查询最终订单
```

accepted_at 由服务端在请求持久化时生成，按权威活动配置验证并保存，不能由客户端指定；价格及 processing_deadline 一并固定。后续 Lua 与成单按这个受理时刻判断开抢窗口，按当前服务端时间判断处理期限。成单重新核对活动归属、价格快照与业务限制；不得因为查询到过期展示值而成交。活动自然结束不拒绝已经有效受理、仍在处理期限内的请求。

Lua 使用同一 hash slot 的 6 个 key：活动元数据、库存、用户、请求 owner、release 去重及订单回补去重；任一 key 类型、schema、元数据或 sentinel 缺失/损坏即 fail-closed，不隐式造 key。占位携带 request_id，同请求重入不能再次扣资格；同用户不同请求按限购规则拒绝。Redis 原子性不覆盖 MySQL/MQ。资格预占成功后仍可能成单失败，因此不向用户宣称“抢购成功”。

发布确认只表示 broker 接收，消费 Ack 表示消费者处理；两者不能互相替代。Outbox 发送记录与待处理请求扫描防止发布中断或通知丢失导致请求永久悬置；发布确认丢失允许重发。消费者以持久请求和订单为准，对重复或已结束消息无副作用；只在对应业务结果提交后 Ack。

瞬时错误采用有次数/时间上限的退避，记录原因后进入可查询的恢复或终态。避免立即无限 Nack 重入；Prefetch 与 Worker 容量匹配。扫描器和正常消费者竞争同一请求时使用相同事务锁和状态条件。

## 6. 资格补偿与 Redis 重建

购买请求必须先持久化再预占：即使进程死在 Lua 成功后、准入事务前，也可扫描 RECEIVED 请求并携带原 request_id 查询占位，继续确认或按规则终止。请求终止与成单互斥，先确认没有订单、持久化 FAILED 和补偿任务，才能释放所属预占。

同代际释放用 Lua 检查 request_id 所有权及已释放标记，避免重试增加多次库存。已成功成单用户占位保持限购约束；成单后不再从 Redis 扣一次资格。订单关单或退款的库存释放由 MySQL RELEASE 流水与同事务回补任务驱动，再按 generation + order_id 的 Redis 去重 hash 增加可售提示，不清除已成单用户的限购标记。库存、开关、owner/request 或去重 sentinel 部分缺失时 Lua fail-closed，不隐式造 key。

Redis 丢数据或代际不明时，不允许直接从“剩余库存”热重建后继续接收写入。当前实现遵守并已验证以下恢复约束：

1. 在 MySQL 关闭该活动准入和库存写入，推进 generation；正常准入、成单和释放事务都检查活动锁与代际，使旧进程不能继续提交。等待既有写事务结束，暂停回补 Worker；只读查询仍可用。
2. 按持久事实整理请求：已有订单以订单结果为准；旧 generation 中无订单的 `RECEIVED` 和 `ADMITTED` 请求一律终止为可查询 `ACTIVITY_GENERATION_CHANGED`，不迁移未知旧预占。用户可用新请求重试。
3. 以一致的 MySQL 快照重建新库存和**所有已有订单用户**的限购标记；`available_stock` 或库存流水核对失败即保持关闭，不能截断后强行开放。
4. 新 generation 不承接无订单旧请求的 reservation；记录快照覆盖的回补任务，确保已计入新库存的旧释放不再追加。旧 generation 的迟到回补不能直接 INCR 新缓存，旧消息只能重新读取当前持久请求再推进。
5. 在停写期间校验库存、请求数、限购标记与待补偿任务，确认新 Redis 数据发布完整后再开放；恢复中断则保持关闭并重做核对。

发布新代际前还必须验证 `total_stock + SUM(inventory_movements.delta) = available_stock`；即使 available_stock 未越界，流水不平衡也不得开放。旧版 Redis 代际缺少回补去重 sentinel 时必须做 fenced rebuild，不能直接补 sentinel 掩盖历史去重记录是否丢失。

这是一种可解释的停写恢复方案，不承诺无损热重建或零停机。MySQL 约束仍是防超卖和重复订单的最终依据。限流在购买请求落库前过滤明显超量流量，但不能宣称抢购链路完全不访问数据库。

## 7. 支付、关单、核销与退款

订单主状态：`PENDING_PAYMENT → PAID → REDEEMED`；未支付可转 CLOSED；PAID 未核销可转 REFUNDING，确认退款成功后 REFUNDED。券状态与订单变更放在同一事务内，或者以订单状态校验阻止无效核销，不允许只更新一边。

- 支付尝试使用稳定请求号，回调校验身份、订单、币种、金额及渠道交易号。重复回调先查询已有支付事实，再推进状态，不能重复发券。回调中断可用模拟器的查询接口补偿。
- 支付成功与到期关单都在事务中锁定订单，通过 PENDING_PAYMENT 条件转换竞争。支付方先成功则关单无效；关单方先成功则订单保持 CLOSED，迟到到账登记支付事实并进入退款补偿，不能恢复为可核销。
- CLOSED 的库存在关单事务中释放一次。迟到支付的退款只退钱，不能再次释放该订单库存；重复支付尝试导致多笔到账也按交易号记录及退款，不能多生成券或重复增加库存。
- 退款申请与商家核销都竞争 PAID 且未核销状态。先进入 REFUNDING 就冻结核销资格；先 REDEEMED 就拒绝普通退款。检查商家店铺归属、券有效性、状态和一次性核销约束。
- 正常退款确认成功后，同事务记录结果、REFUNDED、券失效和一次 RELEASE。已确认永久退款失败可恢复 PAID（仍需符合券使用期限），结果未知时保持 REFUNDING，并用原退款请求号查询或重试；不能换新请求号盲目重退。
- 关单和退款共用每订单唯一 RELEASE；库存递增、流水与状态同事务提交，并以该流水身份生成 Redis 回补任务。券不能因消息重放从已核销状态恢复可用。
- Worker 有界扫描到期 PENDING_PAYMENT 订单并重新检查锁内状态；扫描 PENDING/UNKNOWN 退款时使用稳定请求号重试本地模拟器，再幂等应用结果。真实渠道替换后必须将这一步换成渠道查询/对账契约。

本地模拟器需支持正常成功、重复/迟到/乱序回调、未知结果查询和退款失败。首版不连接真实资金；支付渠道接口替换后要单独验证其身份校验、幂等与对账契约。

## 8. 资源边界与可观测性

用 Redis Lua 限制活动总体和单用户请求速率，资格脚本只做短小原子操作。Redis 异常时暂停秒杀准入并返回受控结果，已持久化请求按状态恢复；不能无条件绕过准入。

通过 RabbitMQ Prefetch、有界 Goroutine Worker、连接池和外部调用超时控制资源；context 传播取消但不强制杀死 goroutine，退出时等待或保留可恢复任务。用户 HTTP 断连不取消已提交购买事实。重复消息、补偿和扫描必须走同一业务约束。

日志包含 request_id、order_id、activity_id、generation、状态变化及失败原因；订单归属校验不能依赖日志或消息自报字段。指标区分请求受理量、成单量、失败量、悬置量、缓存命中与回源、队列等待及处理耗时。

报告必须区分完整响应查询 P95、购买入口延迟、`accepted_at→orders.created_at` 和首次观察终态上界，同时记录超时、失败及未完成请求。订单行时间不是精确 commit 返回时间，HTTP 202 更不是成单。现有量化只覆盖对应源码版本的店铺详情路径，不能外推为活动/优惠券缓存收益。CPU/内存、负载规模、版本与并发条件随结果保存；实测数值见 [benchmark-report.md](benchmark-report.md)。

## 10. 选型依据

- [Ristretto 官方仓库](https://github.com/dgraph-io/ristretto)：Go 进程内缓存；写入可能未接纳，缓存未命中是正常路径。
- [singleflight 官方 API](https://pkg.go.dev/golang.org/x/sync/singleflight)：同一进程内按键合并重复调用。
- [Redis Lua 文档](https://redis.io/docs/latest/develop/programmability/eval-intro/)：脚本执行在 Redis 内原子，不构成跨 MySQL/MQ 事务。
- [RabbitMQ 确认机制](https://www.rabbitmq.com/docs/confirms)：发布确认与消费者确认职责不同。

本轮已核对这些技术用途；实际 Go 依赖版本由本项目 `go.mod` / `go.sum` 锁定，服务端版本与镜像摘要记录在最终环境快照中。
