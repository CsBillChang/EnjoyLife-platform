# 02｜开发任务卡

项目：惠享生活 · Go 本地生活服务平台。更新日期：2026-09-13。

**工程状态：L00–L14 已在 2026-09-22 完成本机实现与验证。** 以下保留原始任务边界作为验收定义；实际结果以[当前进度](03-progress.md)、[量化报告](benchmark-report.md)和代码/原始产物为准。用户动手与面试掌握状态仍独立待验收。

开始前读取 [协作约定](../agent.md)、[项目说明](../README.md)、[当前进度](03-progress.md)，按当前卡查阅 [目标契约](01-design-and-contracts.md)。每次只推进一张卡或其中一个可独立验收的步骤。

先解释目标、文件职责、请求链路和验证方式，再实现；新依赖在对应卡首次需要时核对版本与安装范围。代码完成后记录实际命令、观察结果和未验证项，不能把工程通过写成用户已掌握。

首版采用单体 Go 服务与可控本地支付模拟器，不接入真实资金、真实商户或多套微服务。MySQL 保存业务事实，Redis 和消息队列不能替代订单与库存记录。

## L00｜Go 店铺 CLI

- 前置：无业务代码；先检查现有 Go 工具链，不安装整套后端依赖。
- 范围：使用标准库建立最小模块和入口，按店铺编号查询少量内存示例数据。
- 链路：命令行参数 → 校验 → 查找店铺 → 输出结果；先在一个入口文件中理解类型和错误处理。
- 规则：区分参数错误与店铺不存在，示例数据明确标为测试数据。
- 成功验证：输入有效编号，得到对应店铺名称和地址。
- 失败验证：缺少参数、编号格式错误或店铺不存在时返回明确错误。
- 用户练习：新增一家测试店铺，并查询其编号；对照 Python/C 解释结构体字段。

## L01｜Gin 店铺查询

- 前置：L00 可运行且有实际验证记录；按需引入 Gin。
- 范围：将店铺列表和详情提供为 HTTP 接口，数据仍使用内存示例。
- 链路：HTTP → 路由与参数绑定 → 查询函数 → 统一 JSON 响应。
- 规则：店铺编号、分页参数及错误状态按目标契约处理；暂不建立数据库与缓存层。
- 成功验证：列表、分页和详情请求返回符合契约的响应。
- 失败验证：非法分页与不存在的编号得到对应错误，不暴露运行时内部信息。
- 用户练习：增加一个店铺筛选条件，解释请求经过的函数。

## L02｜MySQL 与 GORM

- 前置：L01 完成；核对本地 Docker 条件，只加入当前所需 MySQL 依赖。
- 范围：建立店铺表及可审查的 SQL 迁移，用 GORM 替换内存读写。
- 链路：接口 → 业务函数 → 数据访问 → MySQL；目录按实际职责逐步拆分。
- 规则：先解释 SQL 与索引，再展示 GORM 调用；不使用运行时 AutoMigrate 代替迁移记录。
- 成功验证：迁移、种子数据、店铺读写与重启后查询均符合预期。
- 失败验证：数据库不可用或约束冲突时返回受控错误，确认没有半完成写入。
- 用户练习：新增店铺营业状态字段及对应迁移，查询启用中的店铺。

## L03｜用户登录与商家权限

- 前置：L02 完成；按契约补充用户、商家身份及店铺归属数据。
- 范围：实现登录与凭证校验，区分普通用户操作和商家管理操作。
- 链路：请求 → 身份中间件 → 业务权限校验 → 带归属条件的数据查询或更新。
- 规则：不信任请求自报的用户或商家身份；商家只能管理自己拥有的店铺。
- 成功验证：用户登录后获取本人数据，商家更新自有店铺信息。
- 失败验证：无效或过期凭证被拒绝，商家越权读写其他店铺被拒绝且无数据变化。
- 用户练习：增加一个需要商家权限的字段更新接口，并构造越权请求。

## L04｜Redis 店铺缓存

- 前置：L03 完成；只为店铺查询引入 Redis，不提前加入秒杀逻辑。
- 范围：实现 Cache-Aside 查询、有限 TTL、空值缓存与数据库更新后的缓存失效。
- 链路：店铺查询 → Redis → 未命中回源 MySQL → 填充缓存。
- 规则：MySQL 是店铺信息依据；Redis 故障时按约定回源，缓存不能替代权限校验。
- 成功验证：首次查询回源、后续命中；修改店铺并失效缓存后能读到更新。
- 失败验证：重复查询不存在店铺、缓存过期和 Redis 不可用时行为符合约定。
- 用户练习：调整测试 TTL，观察一次完整的未命中、命中和过期过程。

## L05｜Ristretto、singleflight 与缓存一致性

- 前置：L04 完成且已有回源观察方式；再引入进程内缓存与请求合并。
- 范围：为热点店铺增加 Ristretto，通过 singleflight 合并同进程同键回源。
- 链路：进程内缓存 → Redis → MySQL；更新后传播失效，短 TTL 为失效遗漏兜底。
- 规则：singleflight 不提供跨实例互斥；两级缓存允许约定时间内的陈旧数据，不宣称强一致。
- 成功验证：并发读取同一冷键时观察回源合并，热点数据可进入进程内缓存。
- 失败验证：模拟失效通知遗漏，确认短 TTL 后收敛；缓存重建失败不污染有效数据。
- 用户练习：比较两个 TTL 配置的回源次数和更新可见时间，记录真实观察。

## L06｜优惠券活动与同步下单

- 前置：L03 的身份规则和 L02 的事务基础完成；当前仍同步创建订单。
- 范围：建立优惠券活动、库存与待支付订单，先完成不依赖 MQ 的交易最小闭环。
- 链路：用户购买 → 校验活动 → MySQL 事务内条件扣减库存、创建订单 → 返回订单。
- 规则：订单唯一键为用户与活动；每用户每活动最多成功创建一单，关闭或退款也不重购。
- 成功验证：有效活动有库存时生成待支付订单，订单与库存变更同时提交。
- 失败验证：并发争抢最后一份库存、重复购买及事务中途失败均不超卖、不重复成单。
- 用户练习：将测试库存改为一份，用两个用户购买并解释其中一个失败的原因。

## L07｜模拟支付与券核销

- 前置：L06 完成；只建立可查询、可重复回调的本地支付模拟器。
- 范围：生成支付尝试、处理模拟成功回调，并让所属商家核销已支付优惠券。
- 链路：待支付订单 → 模拟支付与回调 → 支付记录和订单状态更新 → 商家核销。
- 规则：校验订单、金额及回调身份；支付记录与核销记录可追溯，同一券不能重复核销。
- 成功验证：模拟付款后券可核销，核销后状态和商家记录一致。
- 失败验证：重复回调、金额不符、未支付核销、重复核销及其他商家核销均受控。
- 用户练习：主动重发一次成功回调，检查订单与券记录未增加。

## L08｜超时关闭与退款回补

- 前置：L07 完成；订单支付截止时间持久化，退款仍由本地模拟器处理。
- 范围：增加未支付关闭、未核销退款、库存释放记录及迟到支付补偿。
- 链路：扫描到期订单或申请退款 → 状态条件更新 → 确认释放条件 → 事务回补库存。
- 规则：同一订单的 RELEASE 只一次；关闭后迟到支付进入退款补偿，不能再次回补库存。
- 成功验证：未支付关闭或未核销退款成功后回补一次；退款中的券不能被核销。
- 失败验证：并发支付与关单、退款与核销、重复退款确认及迟到支付均保持状态和库存一致。
- 用户练习：模拟关单后再收到支付成功回调，追踪退款记录与唯一库存释放记录。

## L09｜购买请求、Outbox 与 RabbitMQ 异步成单

- 前置：L06–L08 的同步业务规则已验证；当前再引入 RabbitMQ。
- 范围：持久化购买请求与 Outbox，后台发布消息并异步成单，提供处理结果查询。
- 链路：请求和 Outbox 同事务受理 → 发布 → 消费 → 库存扣减、订单及请求结果同事务提交。
- 规则：受理成功不等于成单；发布可重复，消费按请求身份幂等，数据库提交后才 ACK。
- 成功验证：客户端获取请求编号并查到订单；MQ 临时不可用时已受理请求保留且可恢复。
- 失败验证：发布确认丢失、消费后 ACK 前崩溃和重复消息不重复扣库存或生成订单。
- 用户练习：重放同一购买请求消息，比较订单数、库存及请求最终状态。

## L10｜Lua 资格预占与恢复

- 前置：L09 完成；本卡调整受理链路，先持久请求，再资格预占，最后写准入状态与 Outbox。
- 范围：Lua 原子检查库存提示与买家占位；占位携带 request_id，并为操作增加活动 generation。
- 链路：MySQL 请求 → Lua 预占 → MySQL 准入与 Outbox → 异步事务成单；恢复扫描推进悬置请求。
- 规则：已成单用户不恢复购买资格；未成单失败可按所属请求释放占位并用新请求重试。
- 成功验证：预占重入不重复扣减；重建时停止准入和库存写入、废弃旧代际，以 MySQL 可售库存与全部历史成单用户重建新 generation；旧 generation 中无订单的 `RECEIVED/ADMITTED` 失败为 `ACTIVITY_GENERATION_CHANGED`，不迁移未知预占。
- 失败验证：本卡即验证预占后崩溃、响应丢失与恢复；旧 generation 的迟到回补不能直接 INCR，重建后买家限购仍成立。
- 用户练习：在预占后注入一次中断，恢复服务后按同一请求编号追踪最终结果。

## L11｜活动、用户限流与有界 Worker

- 前置：L10 的资格及恢复逻辑完成；已有单 Worker 的正确成单链路。
- 范围：加入活动和用户限流、有界 Worker Pool、队列容量与消费预取限制。
- 链路：请求限流 → 购买链路 → 有界消费 → context 截止时间与退出等待。
- 规则：限流不替代购买资格与数据库约束；不得启动无上限 Goroutine 或使用无限内存排队。
- 成功验证：不同并发配置下任务持续完成，退出时按约定完成或保留可恢复工作。
- 失败验证：突发请求、慢依赖、取消和进程退出时资源有界，未完成任务可被后续恢复。
- 用户练习：改变 Worker 数量，观察排队时间与资源占用；对照理解 GPM 调度。

## L12｜故障恢复与库存核对

- 前置：L08–L11 各自失败场景已完成；本卡验证组合故障，不补交先前遗漏的关键检查。
- 范围：建立库存与订单核对、悬置请求扫描和可审计的补偿记录。
- 链路：注入故障 → 观察持久状态 → 恢复或补偿 → 按活动核对库存、订单及资格。
- 规则：MySQL 为事实来源；重建遵守停写和代际切换，不能用盲目加库存掩盖差异。
- 成功验证：发布、成单、关单及退款各阶段中断后恢复，库存和唯一订单约束仍成立。
- 失败验证：叠加重复消息、旧代际回补和迟到支付，确认不会重复释放或让已成单用户重购。
- 用户练习：选择一组故障，整理发生点、恢复依据和最终核对结果。

## L13｜pprof 与负载优化

- 前置：L12 完成并有可重复的负载数据；正确性问题先于性能优化处理。
- 范围：采集基线与 pprof，选择一个有证据的热点进行优化，不先罗列优化结论。
- 链路：固定数据与负载 → 采样 → 定位 CPU、内存或阻塞热点 → 修改 → 同条件复测。
- 规则：记录硬件、版本、并发、持续时间、失败数及未完成数，优化后复核交易不变量。
- 成功验证：能说明瓶颈、修改原因及请求延迟、成单结果和资源变化。
- 失败验证：负载超过容量时拒绝或排队符合边界，不以丢任务换取表面吞吐。
- 用户练习：阅读一张性能剖析图，指出一个实际热点并解释其业务来源。
