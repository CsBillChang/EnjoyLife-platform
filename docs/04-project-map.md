# 04｜先看全局：业务、文件与开发路线

项目：惠享生活 · Go 本地生活服务平台。核对日期：2026-09-22。

**先知道系统做什么、文件各管哪一段，再沿真实调用链查看代码和证据。** L00–L14 已实现；本文已从早期“目标目录”同步为当前代码地图。细节以[业务契约](01-design-and-contracts.md)为准，开发顺序见[任务卡](02-work-items.md)，真实完成情况见[进度](03-progress.md)。

## 1. 整个项目为谁做什么

消费者查找店铺、抢购优惠券、付款后到店使用；商家管理自己的店铺和活动、核销消费券。未支付订单可以超时关闭，已支付未核销的券可以申请退款。

```text
消费者：查店铺 → 看活动 → 购买 → 支付 → 出示券码
商家：  管理店铺和活动 ─────────────────→ 核销本店的券
后端：  查询与权限 → 库存和订单 → 支付状态 → 核销或退款
```

这三个方面贯穿项目：查询要能承受热点访问，交易不能超卖或重复成单，支付、退款与核销不能互相冲突。先用接口和本地支付模拟器演示，不必先做前端，也不接入真实资金。

## 2. 当前真实文件

下列是最终验收时的实际主要结构，不再是未实现示例。

```text
local-life-platform/
├── go.mod / go.sum                  本项目依赖及校验记录
├── cmd/
│   ├── shop-cli/                    最小店铺 CLI
│   ├── api/                         HTTP、pprof 与依赖组装
│   ├── worker/                      MQ、Outbox、关单、退款与恢复 Worker
│   ├── admission-init/ / admission-rebuild/
│   └── shop-loadgen/ / async-loadgen/ / benchmark-seed/
├── internal/
│   ├── shop/                       店铺查询与商家店铺管理
│   │   ├── handler.go              读取 HTTP 请求并返回 JSON
│   │   ├── service.go              组织查询、权限与更新规则
│   │   ├── repository.go           使用 GORM 读写店铺表
│   │   ├── model.go                店铺结构体、字段与数据表示
│   │   ├── cache.go                店铺缓存查询、填充和失效
│   │   └── service_test.go         与业务代码就近放置的测试
│   ├── coupon/                     活动列表/详情展示缓存、失效任务与商家标题更新
│   ├── order/                      同步/异步成单、状态机、关单/退款/核销
│   ├── admission/                  Redis Lua 预占、释放、成单后库存回补
│   ├── recovery/                   MySQL 围栏与 Redis generation 重建
│   ├── ratelimit/                  活动/用户令牌桶
│   ├── auth/                       登录凭证、身份中间件和权限帮助函数
│   ├── payment/                    支付/退款适配、模拟器与回调处理
│   └── platform/                   配置、日志、MySQL/Redis/MQ 连接等公用接入
├── migrations/                     审查后执行的建表、加字段和索引 SQL
├── scripts/                        回归、故障、固定负载与 pprof 采集入口
├── artifacts/                      原始评测/故障证据（大样本本地保留）
├── compose.yaml                    独立 MySQL/Redis/RabbitMQ 编排
└── docs/                           契约、进度、验收、量化与面试材料
```

`cmd` 回答“程序从哪里开始”，`internal` 回答“具体工作在哪里完成”。`main.go` 主要组装依赖和启动程序，不承担业务规则；交易、缓存、恢复和权限逻辑均在 `internal` 对应包内。

`shop`、`coupon`、`order` 等按业务分目录，各模块内部再按需划分职责；不另外复制一整套顶层 `service/` 和 `repository/`。`coupon` 负责公共活动展示及缓存失效，不参与交易价格或库存的最终判断；`order` 在 MySQL 事务中重新读取权威事实。单元和真实依赖集成测试均就近放在对应 Go 包中，故障与负载入口集中在 `scripts/`。

`api` 与 `worker` 是两个独立启动入口，但仍属于同一个模块化 Go 项目、共享业务规则；这不要求拆成一套微服务。Worker 负责 MQ 消费、Outbox 发布、超时关单、未知退款和库存回补任务。

## 3. 同一个店铺模块为什么有几个文件

以已实现的 `GET /shops/42` 为例，下表对应 `internal/shop/` 的真实分层职责。

| 文件 | 你在里面主要编写什么 | 具体例子 |
| --- | --- | --- |
| `handler.go` | HTTP 参数读取、基本格式校验、调用业务函数、响应状态和 JSON | 把路径里的 `42` 转成编号，格式错误返回 400 |
| `service.go` | 业务条件判断、组织缓存/数据访问、管理操作的归属校验 | 查询店铺详情；商家修改前检查是否属于本店 |
| `repository.go` | 数据查询和保存，封装 SQL/GORM 操作并传播错误 | 按编号 SELECT 店铺；按店铺归属条件 UPDATE |
| `model.go` | 用结构体描述数据；输入、输出、持久化模型按实际需要区分 | 店铺 ID、名称、地址、营业状态，不在结构体里隐藏整套业务 |
| `cache.go` | 把缓存策略与店铺数据联系起来 | 生成缓存键，未命中回源，更新后失效 |
| `service_test.go` | 用输入和可观察结果验证规则 | 别的商家不能修改该店，错误操作不改变数据 |

初始查询链路是 `Gin 路由 → handler → service → repository → MySQL`，结果沿相反方向返回 JSON。`model.go` 提供这些函数共同使用的数据类型，并不是每个请求必须经过的独立执行步骤。

可以用 Python 对照：handler 类似 Web 框架接收请求的函数，service 是你编写的普通业务函数，repository 封装数据库调用，model 像用于传递字段的 dataclass。Go 将这些函数和类型组织在包中，不需要每个文件都写一个类。

事务不是“每个 repository 自己提交一次”。例如订单与库存必须一起成功，业务层确定这次操作的事务范围，各数据操作使用同一个事务连接；可直接从 `internal/order/` 的购买和履约代码跟踪。

## 4. 技术栈放在哪，哪些需要自己写

| 类别 | 技术与位置 | 我们实际编写的内容 |
| --- | --- | --- |
| 编译进 Go 程序的库 | Gin、GORM、Ristretto、singleflight | 路由和处理函数、数据访问调用、缓存策略及回源合并逻辑 |
| 独立运行的程序 | MySQL、Redis、RabbitMQ | 连接配置、客户端调用、表与索引、Lua 脚本、消息格式和处理逻辑 |
| Go 语言与诊断能力 | Goroutine、context、pprof | 有界并发、超时传递、退出流程和性能采样入口 |
| 本地环境编排 | Docker Compose | 需要哪个服务、版本、端口、健康检查及本地数据目录等配置 |

安装 Gin 不会自动生成店铺业务，使用 GORM 也不会替你设计事务。MySQL、Redis 和 RabbitMQ 的服务端无需自己重写，但我们要理解其约束，编写接入和失败处理代码。

`platform/` 负责建立和关闭连接、读取配置等公用细节；“用户能否买券”“订单能否退款”仍放在相应业务模块。Redis 店铺缓存与 Redis 秒杀资格使用不同规则，不因为共用 Redis 就混为一个功能。

## 5. 运行时：三条需要先看懂的链路

**店铺查询，从数据库查询逐步增加缓存。** 最初只有 MySQL，L04 引入 Redis，L05 才增加进程内缓存。

```text
请求 → Gin/handler → 店铺 service → Ristretto
                                    ├─ 命中有效展示值：返回
                                    └─ 未命中 → Redis
                                                ├─ 命中：返回并尝试填充本地缓存
                                                └─ 未命中 → repository → MySQL
                                                               └─ 返回并填充缓存
```

这种“先查缓存，未命中再查数据库”的方式称为缓存旁路。商家更新时先提交数据库修改，再失效缓存；短 TTL 与失败重试处理遗漏。缓存允许约定范围内的短暂陈旧，不能直接决定交易价格或库存。singleflight 合并同进程同键回源，无法让多个进程全局只查一次数据库。

**同步买券，先把交易正确性做实。** L06 开始时没有异步成单，也没有 Redis 资格预占。

```text
购买请求 → 身份校验 → order service
  → 同一个 MySQL 事务：校验活动、条件扣库存、创建订单和库存流水
  → 提交成功 → HTTP 201 + 订单号
```

事务失败则全部回滚；用户、活动唯一约束防止重复成单。每用户每活动最多成功创建一单，关闭或退款也不重购。随后 L07–L08 增加支付模拟、核销、关闭、退款及竞争验证。

**最终异步抢券，把请求受理与创建订单分开。** L09 加入异步成单，L10 增加资格预占，L11 加强限流和并发控制。

```text
请求 → 登录与限流 → MySQL 持久保存 purchase_request
  → Redis Lua 按 request_id 原子校验并预占资格
  → MySQL 事务：记录 ADMITTED 准入状态 + Outbox 待发消息
  → 发布到 RabbitMQ → Worker 接收
  → MySQL 事务：条件扣库存 + 订单 + 库存流水 + 请求结果
  → 提交后确认消息；用户按 request_id 查询成单结果
```

HTTP 202 表示持久请求正在处理，不能显示为已购券；通过 Lua 也只代表取得资格。MySQL 保存最终订单、库存、支付和核销事实。先持久化请求再预占，才能在预占后程序中断时找到恢复依据。

Outbox 是与业务同事务保存的待发送记录；后台可重试发布。消息可能重复，Worker 用请求标识、事务和唯一约束防止重复扣库存、重复建订单。客户端断开连接不会自动撤销已经提交的订单。

Redis 资格数据损坏时采用停止准入与库存写入、切换 generation、依据 MySQL 重建的方案；旧代际不能直接向新缓存加库存。已有数据如果缺少新版去重 sentinel，必须按活动做 fenced rebuild，详见[业务契约](01-design-and-contracts.md)。

## 7. 一个需求会改哪些文件

以 L02 的练习“给店铺增加营业状态，支持只查询营业中的店铺”为例：

1. 在 `migrations/` 增加字段迁移，明确已有店铺的默认值；修改 `model.go` 的结构体表示。
2. 在 `handler.go` 解析筛选参数并检查格式；在 `service.go` 定义筛选和修改规则。
3. 在 `repository.go` 增加对应查询条件和更新语句，避免只在返回结果中临时隐藏店铺。
4. 增加查询与错误输入测试，并验证只有所属商家能改状态。
5. L04–L05 已引入缓存时，还要检查缓存值、查询键和更新失效是否覆盖这个字段，并验证更新后查询会收敛。
6. 更新接口示例和[进度](03-progress.md)，记录实际执行结果和你亲手修改的部分。

先用这份地图认清“这个需求经过哪些模块、数据最终存在哪里”；阶段末复盘从三条运行链路定位核心文件，再对照故障实验和量化证据讲清设计取舍。
