## 已执行步骤

1. **核对采样对象与负载重叠**：保存 API/Worker 的准确 PID、二进制哈希、启动参数（脱敏）、Go 版本、端口、起止时间和请求完成数。先查清旧 CPU 样本为何稀少，排查是否抓错进程、负载先结束、进程主要阻塞或平台采样问题，不将任何假设写成结论。
2. **提供有界诊断配置**：为确有分析需要的 API/Worker 增加 mutex/block 采样开关和频率，默认关闭，启用参数留档。不同 profile 分轮采集以减少干扰；只使用回环调试端口。保持正常运行不承担高频采样开销。
3. **准备代表性负载**：店铺热读、同一热点冷缓存并发回源/受控失效、同步与异步抢券和消费中断分别运行。只操作独立实验活动和数据，不清空 Redis、不删除卷，不故意在业务代码加锁或泄漏来制造“发现”。先用小规模并发预检，再选择设备可承受的固定并发和持续时间。
4. **分别采集**：CPU；`heap` 的 `inuse_space/inuse_objects`；`allocs` 的 `alloc_space/alloc_objects`；mutex 与 block。分配累计量使用同一进程的前后快照或对应时间窗，不把启动累计分配当成测量窗口增量。记录 GC 条件，区分累计分配、存活堆和 RSS；不能只凭堆增长宣称内存泄漏。
5. **定位到代码**：保存 `go tool pprof -top`、`-list` 和必要的调用图，说明采样类型、样本量/等待时间、项目调用栈与第三方库边界。mutex 等待与 MySQL 行锁等待不是同一指标；数据库锁需另外查数据库证据。block 中空闲队列等待不自动等于业务瓶颈。
6. **有依据才改动**：先记录至少一个能重现的锁等待/内存分配来源及其业务条件，再选择值得修复的点。若锁等待不显著，记录可观测结果与限制，不能编造瓶颈或收益；样本不足则保持该项未完成，并提出有限的下一轮采样方案。
7. **同条件对照**：如做优化，以相同数据、负载、采样参数和环境比较 profile；正式延迟/吞吐在关闭额外采样后复测，竞态检测独立运行。保存错误率、完整响应、吞吐、P95 与分配/等待变化，不只选择改善指标。

## 执行结果

- 诊断开关已接入且默认关闭；正式轮显式使用 mutex fraction 1、block rate 1,000,000 ns。采样 PID、端口监听、二进制哈希、脱敏配置和 UTC 时间线均已保存。
- 对 CPU、mutex、block、allocs、heap 分别使用新 API 进程采集：100 并发、10 秒预热、45 秒负载，30 秒 profile 完整落在负载窗口内。新 CPU profile 得到 68.78 CPU 秒样本，旧 40 ms 样本保留但排除。
- mutex 的 goroutine 累计等待为 1,689.16 ms/30.01 秒；项目 `singleflight.Do` 链路占 3.60%，未发现值得改动的业务锁热点，因此未实施锁优化。
- allocs 定位到店铺详情动态 `gin.H`/JSON map 编码分配。仅将成功详情响应改为 typed struct 后，handler 微基准从 25 降至 20 allocs/op，B/op 约降低 6.2%；应用 heap 轮按完整响应归一化的分配字节与 malloc 分别约降低 14.30% 和 17.26%。
- 关闭 mutex/block 诊断后，优化前后各做 3×60 秒交错对照。P95 中位变化 -0.16%，吞吐中位变化 -1.46%，轮次方向不一致；因此只接受分配下降，不声称 P95 或吞吐提升，也不声称修复内存泄漏。
